# Research: Alternative Route (Detour) Plotting — Phase 0

All findings below resolve the unknowns flagged while filling the Technical Context of [plan.md](./plan.md). Every decision was grounded in the real codebase (surveyed with file:line citations) and the clarified spec (Q1 = existing Stops only, Q2 = minimal server validation). Design decisions are consistent with `docs/adr/` (ADR-0008, 0012, 0013, 0014, 0015, 0016) and `docs/CONTEXT.md`.

---

## R1 — Where the "Add alternative route" action lives

- **Decision**: Add an **"Add alternative route"** action to the existing floating `PlotActionBar` (`apps/admin/src/features/routes/PlotActionBar.tsx`), disabled while the open Direction has **no base polyline** (post-touch empty direction). Opening the editor shows the detour editor surface over the workspace (right panel swaps to detour properties; floating-bar focus shifts to detour-specific actions).
- **Rationale**: The floating bar is the established primary-action surface for route/plot work in the workspace (ADR-0015); a direction with no base path has nowhere to anchor entry/exit, so plotting is physically impossible. The spec's FR-010…FR-012 actions are all "inside the workspace", which this satisfies without new page routes.
- **Alternatives considered**: (a) A new page/route for detour plotting — rejected: breaks the workspace single-surface model (ADR-0014) and adds navigation state; (b) a button per direction row in the left list — rejected: poor discoverability while plotting, mixes list and editor concerns.

## R2 — Road-following for the detour loop

- **Decision**: Reuse the base-path editor's road-following path verbatim: client calls the same `snapPreview` (`apps/admin/src/features/routes/routesApi.ts:198-207` → `GET /api/admin/mapbox/directions`, guarded `token` + proxy 25-waypoint chunking + `data.snapped_path.coordinates`), bound through `detourStore.bindSnapFetcher`, debounced ~300 ms like `plottingStore` (`apps/admin/src/lib/plottingStore.ts:216`). The loop request is `snapPreview([entry, ...waypoints, exit])`. **Straight-line fallback + warning** on failure/no-token stays (mirrors base editor; straight fallback may be persisted with the visual "follows straight line" warning copy anchored to FR-009 — verified independently of the base editor path).
- **Rationale**: Spec FR-005 requires road-followed loops; the proxy is the single existing implementation (ADR-0016 needs the public token, already used by plotting). Reusing it means zero new server surface and identical UX behavior (parity with Prio record lesson).
- **Alternatives considered**: (a) Client-side straight loops only — rejected: violates FR-005; (b) a new `/detours/snap` endpoint — rejected: **no new endpoints** (clarification Q2's frame) and the existing proxy already handles chunking.

## R3 — Snapping entry/exit onto the base polyline

- **Decision**: Add a new pure helper `projectPointOnPolyline(point, line) → { coordinate: CoordinatePair; index: number; distanceMeters: number }` in `apps/admin/src/lib/coords.ts`, using haversine point-to-segment projection mirroring the server's segment math in `assertPointOnLine` (`apps/server/src/domain/validation.ts:29-64`). The admin clicks near the base path; the picker sets `entry`/`exit` to the projected coordinate and remembers the base-polyline `index` (used for travel-order checks and additional-distance slicing). `nearestCoordIndex` (`lib/coords.ts:28-45`) is **vertex-only** and insufficient (click between vertices would snap to a corner).
- **Rationale**: Client snap previews must intersect road geometry cleanly; entry/exit must land ON the base polyline so the committed loop composes visually (`entry + loop + exit` replaces `base[entry..exit]`) and server `assertPointOnLine` (30 m) always passes. This is the same relationship the server describes, stated once on the client (`coords.ts`, the admin's single math home).
- **Alternatives considered**: (a) Let the server's 30 m tolerance absorb a raw click — rejected: produced visually loose loops and drift between client previews and saved geometry; (b) reuse `nearestCoordIndex` — rejected (vertex-only, see above); (c) implement via MapLibre `map.project`/viewport only — rejected: NOT a geometry projection, wrong tool.

## R4 — Minimal server-side validation (FR-023, SC-014)

- **Decision**: The server gets exactly ONE new invariant, enforced in the existing handlers:
  - **Loop endpoints on entry/exit**: `assertDetourLoopEndpoints(loop, entry, exit)` in `domain/validation.ts` — `loop[0] ≈ entry` and `loop[last] ≈ exit` within `DETOUR_ON_LINE_TOLERANCE_METERS = 30` (reusing the existing detour-scoped constant), and `entry ≠ exit` (degenerate zero-length loop rejected). Called on **POST** always; on **PUT** when `detour_polyline` **or** `entry`/`exit` is supplied. Implementation uses the existing JS haversine `coordinatesDistanceMeters` (`apps/server/src/domain/derive.ts:47-61`).
  - Already covered and left as-is: **entry/exit on line** (`assertPointOnLine`, POST: `detours.ts:54-55`, PUT: `detours.ts:113-118`) and **`additional_distance_meters ≥ 0`** (zod `z.number().int().min(0).nullable().optional()`, `packages/shared/src/schemas/domain.ts:110`) → 422 `VALIDATION_ERROR` via the type-provider.
  - **Travel order (entry index < exit index) stays CLIENT-side only** (detourStore refuses save + shows the "travel order" dialog with a swap action, spec FR-004). Ordering requires walking the base polyline and is editor-specific; the clarified minimal set (Q2-B) deliberately excluded it.
- **Rationale**: Q2 → minimal structural validation on existing endpoints (no new endpoints). These are cheap, unit-testable guards that close the real corruption hole — silent fallback loops could otherwise persist with mismatched endpoints and poison commuter geometry/distance. The JS-side choice keeps validation in the same engine + tolerance set as the existing checks (consistent behavior, testable without a DB).
- **Alternatives considered**: (a) SQL/PostGIS-side checks reusing the dormant `pointOnLineMeters`/`pointDistanceToLineMeters` helpers in `db/queries.ts` (must `::geography` for meters) — rejected: introduces a SECOND validation engine and DB round-trips inside handlers for a pure-geometry check the JS domain layer already owns; the constitution's `::geography` rule governs SQL distance math, and this feature adds none (no violation: we add JS distance math, consistent with `assertPointOnLine`); (b) full endpoint+ps strict validation (per-segment containment, self-intersection) — rejected: out of the Q2 minimal scope, high complexity, low payoff for a thesis-scale single-admin tool.

## R5 — Distinct visual style for detour loops (FR-012)

- **Decision**: A new layer kind `"detour"` in `apps/admin/src/features/routes/map/RouteLines.tsx` + token set in `map/constants.ts`: detour polylines render **dashed and slightly thicker** than base lines, colored from the existing ROUTE/line palette per detour (repeatable cycle), with **signal amber strictly reserved** for interactive/active states. Committed detour loops draw the loop + the replaced base segment REMOVED (composed path = full base minus `base[entry..exit]` plus loop). Draft/unsaved loops reuse the existing draft styling semantics.
- **Rationale**: DESIGN.md reserves amber for attention state; a default amber detour line would fight every active-interaction cue. A dash + width differential is legible over the base solid line without new hues, and per-detour palette cycling keeps several detours on one map distinguishable (admin needs to see multiple alternatives at once).
- **Alternatives considered**: (a) Hardcoded single color — rejected: multiple detours become indistinguishable; the exact treatment is deferred to implementation per the spec's "distinct visual identity" note, so this documents the constraints, not the final token.

## R6 — Where detours live in the workspace UI

- **Decision**: A nested **"Detours"** section in the right-side panel under the open Direction (label, active toggle, open/edit, remove with styled confirm), synchronized with the server list (`loadDetours` shape). "Add alternative route" (R1) transitions the panel into the Detour editor; editing an existing detour opens the same editor pre-filled from the server payload.
- **Rationale**: The workspace is one map + two columns (left: route tree, right: properties/plot). Detours belong to exactly one Direction; nesting under it in the properties panel keeps the map surface clean and the association explicit (FR-010/FR-013 read/persist). No new tabs.
- **Alternatives considered**: (a) Separate tab/page listing detours — rejected (R1 reasoning); (b) drawing detours directly on the left tree — rejected: tree is for routes/directions/stops, detours are child geometry (ADR-0008), and tree nodes need map anchor identity that detour nodes would not have.

## R7 — Drafts, Undo/Redo, and save safety for the detour editor

- **Decision**: Reuse the established safety behaviors, never re-design (ADR-0014):
  - **Draft**: extend the localStorage draft story with a NEW namespaced payload `DetourDraftPayload` under `komyuter.draft.{routeId}.{directionId}.detours` (draft key pattern per `apps/admin/src/features/routes/draft.ts:23-34`; the base path uses the parent namespace, so detours must NOT collide). 24h TTL; restore-offer banner on re-enter; payload holds mode (new vs `detour_id` being edited), entry, exit, waypoints, loop, field values, notable stops, and the history stack.
  - **Undo/Redo**: the detour planning store keeps its own history stack reusing the `plottingHistory` pattern (entries: entry/exit placed, waypoint added/removed, loop drawn, field edited, notable stop toggled) with the same hotkeys and toolbar affordances as the base editor.
  - **Confirm/toast/conflict**: styled confirms (AlertDialog) for destructive ops; sonner toasts for save/failure; existing conflict surface (409 plate + "load latest" reseed in `RouteWorkspaceProvider`) reused for detour saves — mapped to the same `ApiError` mechanism. Detours carry no per-row version column today; the feature relies on the existing direction-level conflict handling and documents that no new server versioning is added (single-admin thesis scope; noted in spec Edge Cases).
- **Rationale**: Parity with the base editor's safety story is explicitly required (spec US1/FR-008, FR-017); a separate namespace is the only correct way to add a second draftable surface without clobbering the base path draft.
- **Alternatives considered**: (a) Reuse the base draft object + add detour fields — rejected: serialization islands would make base-path saves write detour junk into the route payload; (b) no drafts for detours — rejected: violates the same "never lose the admin's work" bar.

## R8 — Notable stop sourcing (existing Stops only)

- **Decision**: The notable-stop picker offers **only existing Stops**: candidates = stops of the owning Route's Directions (already in the workspace detail payload) filtered by name search, plus a "near the loop" section ranked by distance from the loop polyline (nearest vertex via `coordsDistanceMeters`, consistent with `nearestCoordIndex` semantics). Selecting yields `{ stop_id, name, is_detour_only: false }`; a checkbox toggles `is_detour_only` (meaning: this stop is notable only in the detour context — still references an existing stop). No stop creation UI (per Q1; stop creation remains a future feature — spec's deferred work).
- **Rationale**: Q1 decided `notable_stops` must reference real `stop_id`s (the shared schema has NO FK — `packages/shared/src/schemas/domain.ts:22-26` — so the editor is the guard). Limits candidates to the route's own stops: sensible scope, name search covers the rest.
- **Alternatives considered**: (a) Global stop search across all routes — rejected: noise, needs an extra endpoint (no new endpoints); (b) allow inline stop creation — explicitly rejected by Q1; (c) FK enforcement server-side — rejected: schema change, out of Q2's minimal set (and the clarifying question's answer was UI/editor-level sourcing).

## R9 — Additional distance, computed exactly (FR-011)

- **Decision**: Client computes `additional_distance_meters = loopLength − baseSegmentLength` exactly: loop length = `polylineDistanceMeters(loop)` (existing haversine sum, `lib/coords.ts:169-178`); replaced base segment = slice of the base polyline between the snapped `entry.index` and `exit.index` (inclusive), length summed with the same helper (new tiny pure helper `polylineSegmentLength(line, i0, i1)`). Displayed read-only via `formatDistance`; sent as an integer in the save payload. The server stores whatever valid (≥ 0) integer arrives — it does not recompute (existing behavior preserved; the admin's geometry is the source of truth, and exactness is guaranteed by construction).
- **Rationale**: Spec FR-011 demands "exact" — deriving from the same geometry the server persists guarantees displayed == stored without a second engine (and without PostGIS `ST_Length` divergence). `polylineDistanceMeters` is already the admin's sole length implementation.
- **Alternatives considered**: (a) Server computes via `ST_Length(::geography)` on save and returns it — rejected: changes existing semantics, adds a DB round-trip, and risks float divergence from the displayed value (exactness principle means display must equal stored); (b) hand-entered field — explicitly rejected by the spec.

## R10 — Save payload mapping and `is_active`

- **Decision**: Morphing the client draft → the existing `createDetourSchema`/`updateDetourSchema` (`packages/shared/src/schemas/domain.ts:105-118`): label = auto-generated "Detour from {entry stop-ish label} to {exit stop-ish}" editable (min 1), `commuter_instruction` required (min 1), `driver_instruction` optional, `notable_stops` array (schema-validated), `additional_distance_meters` from R9. `POST` sends NO `is_active` (create schema has none; DB default `true`); `PUT` sends the fields being edited (patch semantics, `detours.ts:120-138`) — **send `is_active` only from the list's active toggle**. `entry`/`exit` sent as Point GeoJSON (`{type:"Point", coordinates:[lng,lat]}`) and `detour_polyline` as LineString GeoJSON, exactly like `detours.ts` echoes them back (201 `/`200 envelope: `{ success, data }`).
- **Rationale**: The clarified scope is "consume the existing CRUD" — payload shapes are fixed by the shared schemas, so the editor maps ONTO them rather than changing them. Active-toggling through the same PUT endpoint (soft state) keeps the two surfaces consistent (ADR-0012 keeps activation semantics out of the loop; the toggle is the existing field).
- **Alternatives considered**: (a) Extend the shared schemas (e.g. `is_active` on create) — rejected: no shared-field changes (constitution III, clarified scope); (b) separate activate endpoint — rejected: no new endpoints.
