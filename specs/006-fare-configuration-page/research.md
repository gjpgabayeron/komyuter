# Research: Fare Configuration Page

Phase 0 output for `specs/006-fare-configuration-page`. Each unknown from the plan's Technical Context and each design choice is resolved here as `Decision → Rationale → Alternatives considered`. All NEEDS CLARIFICATION items from the Technical Context are resolved below (none remain).

## R1. Server: route-reference delete guard (spec Clarification Q1)

- **Decision**: In `apps/server/src/api/fare-configs.ts`, the `DELETE /fare-configs/:fareConfigId` handler gains a guard before the existing last-default check: `SELECT ... FROM routes WHERE fare_config_id = :id AND is_active = true LIMIT 1`; if a row exists, throw `conflict(...)` ("Cannot deactivate fare configuration referenced by active Routes"). The `GET /fare-configs` list serializer is extended with `active_route_count` (aggregate LEFT JOIN count over active Routes) so the page can disable the delete action up front (per the clarification: "the page disables delete for those rows with a clear explanation").
- **Rationale**: The schema already has the FK + index (`routes.fare_config_id` references `fare_configs`, `routes_fare_config_id_idx` in `apps/server/src/db/schema.ts:103-111`), so the guard is a cheap query-time check — no migration. `is_active = true` scopes the guard to Routes actually in service; a deactivated Route's reference does not block cleanup. Exposing `active_route_count` in the list makes the client-side disable deterministic and avoids a second routes fetch; the delete button is disabled when `is_default || active_route_count > 0` (with exactly-one-default enforcement, `is_default` implies sole default).
- **Alternatives considered**: Client-only disable via a separate `GET /routes` fetch (rejected: couples the fares page to route-list caching and leaves the API open to direct deactivation); hard-delete instead of deactivate (rejected: spec FR-007 mandates deactivate, matching existing behavior).

## R2. Admin UI primitives: shadcn Base UI availability (plan Technical Context NEEDS CLARIFICATION)

- **Decision**: Generate `dialog`, `alert-dialog`, `switch`, and `table` with `pnpm dlx shadcn@latest add dialog alert-dialog switch table` in `apps/admin` (style `base-nova`, `@base-ui/react` ^1.6.0, React 18.3.1). All four exist in the base-nova registry and require only React 17/18/19-compatible Base UI primitives (verified against registry item JSONs and `@base-ui/react` peer deps).
- **Rationale**: The admin already generates every UI primitive via the shadcn CLI on Base UI (005 feature convention: "use CLI install script and avoid manually creating the files"). `dialog` hosts the create/edit form; `alert-dialog` hosts the delete confirmation; `switch` provides set-as-default and active toggles (no color-only state — text labels accompany each); `table` renders the tabular list (Base UI ships no table primitive, so shadcn's `table` is a styled semantic-HTML wrapper — correct choice for tabular fare data and free accessibility).
- **Caveats**: Base UI has no table primitive — shadcn's `table.tsx` is a semantic `<table>` wrapper; use it with a `caption`/header scope for a11y. The CLI rewrites `icon-placeholder` imports to `lucide-react` per the local `components.json` `iconLibrary` (already verified in the existing generated components).
- **Alternatives considered**: Hand-writing the four primitives (rejected: violates the CLI-install convention); using only existing components (rejected: no dialog/switch/table exist; `sheet` alone is a poor fit for a modal form with toggles).

## R3. Client data-fetching pattern (spec FR-001, FR-009, FR-010)

- **Decision**: `features/fares/api.ts` wraps the existing envelope-aware axios client (`lib/api.ts`) in typed calls — `listFareConfigs()`, `createFareConfig(payload)`, `updateFareConfig(id, patch)`, `deactivateFareConfig(id)` — each typed against the `@komyuter/shared` `FareConfiguration` / `createFareConfigSchema` shapes. `features/fares/queries.ts` exposes `useFareConfigsQuery` (`useQuery`, key from a new `lib/queryKeys.ts` factory) and three mutations that `invalidateQueries` the list key and fire sonner toasts via the existing toast helper conventions.
- **Rationale**: Matches the documented admin data layer (`@tanstack/react-query` 5, axios envelope client, `features/*/use*Queries.ts` + `lib/queryKeys.ts` per `docs/ADMIN.md` §3/§10.1). The response interceptor already unwraps `data` and normalizes failures to `ApiError { code, message }`, so the api module stays thin and every failure surfaces a server message (FR-008). Invalidation after each mutation guarantees the list reflects persisted server state (FR-009).
- **Alternatives considered**: Component-local fetching with `useEffect` (rejected: react-query is the established stack and gives loading/error/stale states for FR-010 for free); duplicating query keys inline (rejected: a single factory prevents key drift).

## R4. Form validation and formatting (spec FR-004, FR-011, SC-006, SC-007, SC-011)

- **Decision**: Pure, unit-tested helpers in `features/fares/validation.ts` and `features/fares/format.ts`. `validateFareConfigForm(values, existing, selfId)` returns field errors: label required (trimmed) and unique (case-insensitive against `existing`, excluding `selfId` on edit); `base_fare`, `base_distance_km`, `rate_per_km` non-negative finite numbers; `student_discount_pct`/`senior_discount_pct` in `[0, 100]`. `formatPeso` renders exact two-decimal pesos with ₱ when fractional (₱13 → "₱13", 13.5 → "₱13.50"), `formatKm` 1–2 decimals, `formatPct` integer %. The form also blocks submit when `is_default && !is_active` ("Reactivate before making default", FR-015).
- **Rationale**: Strict TS + the constitution's Precision Is Trust demand exact display and deterministic validation; pure functions are cheap to test and cover the riskiest logic (SC-006/SC-007/SC-011). Duplicate-label detection is a client-side check against the already-fetched list — no extra request (per clarification Q3). Default-on-inactive is blocked client-side before submit AND server-side: the PUT handler rejects an update that would leave `is_default && !is_active` (CONFLICT), so FR-015 holds even for direct API callers (see `contracts/fare-configs-api.md`).
- **Alternatives considered**: Server-round-trip for every validation (rejected: latency + no inline errors); inline validation logic in the component (rejected: untestable without component harness).

## R5. Server test strategy (server TDD gate)

- **Decision**: Extend `apps/server/tests/integration/crud.test.ts` (which already covers fare-configs create/update at lines 82-115) with tests written FIRST: (a) DELETE returns 409 CONFLICT when an active Route references the config; (b) DELETE succeeds (soft-deactivates) when only an inactive Route references it; (c) DELETE of the sole default still returns 409 (existing behavior, regression-guarded); (d) GET list includes `active_route_count` with correct counts (0, referenced-by-inactive, referenced-by-active). Uses the existing `helpers.ts` + `buildApp` + `auth()` + `uniqueRouteId` conventions; the routes POST payload pattern is taken from the existing tests.
- **Rationale**: AGENTS.md mandates server tests FIRST with `pnpm --filter server test` green before commit; the existing crud test file already seeds the auth/admin fixtures and route creation, so the guard tests slot in without new scaffolding. `active_route_count` is asserted in the same suite.
- **Alternatives considered**: A new `fare-configs.test.ts` (acceptable — decided at implementation if the file grows; the plan targets `crud.test.ts` to reuse the route-seeding helpers already there); testing the guard only manually (rejected: TDD gate).

## R6. Delete-flow UX without route data on the page (spec FR-007, SC-005, SC-009)

- **Decision**: The delete button is disabled with an explanatory tooltip/label when `active_route_count > 0` or `is_default`; an `alert-dialog` confirm is required otherwise; the DELETE request still runs and any CONFLICT from the server is surfaced as an honest error toast with the list unchanged (defense-in-depth for races).
- **Rationale**: The clarification requires the disable-up-front behavior, and the server guard (R1) covers races where a Route is created between list load and delete. Both layers together make SC-005/SC-009 deterministic.
- **Alternatives considered**: Always allow the attempt and rely on the server error (rejected: contradicts the clarification's "delete action unavailable ... with a clear explanation"; worse UX).

## R7. Visual presentation of default/inactive states (spec FR-012, FR-013)

- **Decision**: Default and active status are shown with text badges (e.g. "Default", "Inactive") built from the existing `badge` primitive, accompanied by color only as a secondary cue; row actions use icon buttons with `aria-label`s; the dialog is keyboard-operable (Base UI handles focus trap); focus rings and contrast follow the appshell WCAG AA pass.
- **Rationale**: FR-012 forbids color-only state; the appshell already established the token/badge conventions and a11y baseline that this page must not regress. Route Sign grammar is inherited from the shared `index.css` tokens — no new visual system.
- **Alternatives considered**: Status pills with color-only differentiation (rejected: FR-012); a bespoke StatusBadge shared component (deferred: `badge` suffices at this scale; ADMIN.md's `components/shared/StatusBadge` remains a later polish item).
